# 開發流程

## 1. 問題探索（Gate）

開發的起點，需要使用者參與。目標是讓雙方對「要解決什麼問題、成功條件是什麼、改動在哪裡」同時有共識。

這個階段是探索性的：使用者提供目的與背景，agent 可自由查閱相關程式碼以支撐討論；需要定位技術目標時，執行**技術探索**（依 workspace 能力）。兩者相互補充，不需要嚴格順序。

完成條件：
- 雙方對成功條件有共識
- 已確立目標系統與程式碼位置

若目標無法確立，先回報不確定性與已查證的線索。

## 2. 規劃

### Requirement Fit Gate

開始規劃前先判斷需求與現行系統的關係：

1. 需求型態：問題描述、指定解法、review 意見，還是 debug 後的修復假設？若只有解法，先回推原問題與成功條件。
2. 系統相容性：是否可能改變既有行為語意或系統契約？
3. 結論：**相容** 或 **不確定**（附上證據與未釐清問題）。

### 停下條件

命中以下任一項，輸出計畫草案，進入計畫確認 gate：

硬性停點（任一項）：
- fit 結論不確定，或需要業務 / 產品決策
- 跨系統、跨服務，或涉及遠端狀態改變
- debug 尚未釐清 root cause

風險訊號（兩個以上）：
- 存在多種合理解法
- 需要改多個模組或 layer
- 驗證不是單一步驟就能確認
- 交付順序會影響做法

### 計畫內容

至少包含：

1. 成功條件
2. Fit Gate 結論（相容性、證據、未決問題）
3. 已確認事實 / 假設
4. 改動步驟與目標位置
5. 驗證方式
6. Commit 規劃：每個 commit 的範圍、主要改動、驗證點與建議訊息

Commit 規劃原則：可以分別理解、驗證、review 的改動就拆；拆開會留下不可運作的中間狀態就不硬拆。

## 3. 計畫確認（Gate）

計畫送使用者審閱。取得明確同意後才進入實作。

## 4. 實作與審查

### 實作原則

- 優先小步修改，讓每一步可審核、可驗證
- 先定義預期行為，再實作
- 可測的行為變更，先補失敗測試；無法自動化時，定義可重跑的驗證案例

### 審查迴圈

每輪實作完成後，發起**審查任務**：

- 審查通過 → 進入驗證
- 審查未通過 → 依審查結果修正，重複直到通過

每次 commit 前列出範圍、訊息與主要變更，待確認後執行。

## 5. 驗證

確認改動在功能上正確。必須有 fresh evidence，不得只靠推測宣稱完成。

驗證方式依任務性質決定。驗證失敗回到第 4 節處理。

## 6. 交付確認（Gate）

驗證結果送使用者確認。取得同意後執行交付。

## 7. 交付

發起**交付任務**（依 workspace 交付方式執行）。
