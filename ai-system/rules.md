# 規則

先讀這份。若 agent 只記得幾件事，記這裡就夠了。

## 1. 最小硬限制

日常任務 agent 只需要內化最小限制、任務流程入口與高回頭成本停下 gate。

1. 高回頭成本要先交代方案。若方向錯了會難以回復、重做成本高，或會形成共享協作承諾，先停下等使用者確認。
2. secret、token、password 不得寫入 `.md` 或任何 git-tracked 檔案。
3. 沒有證據的內容不得寫成事實；推測與假設必須標明。
4. 系統現況優先於文件與舊腳本。

邊界不清時看 `ai-system/constraints-detail.md`。

## 2. 任務流程入口

需要判斷任務類型或流程時，看 `ai-system/skills/README.md`。命中 skill 後，先讀對應 `SKILL.md`，再依 skill 指示讀 references / knowledge。

不要在入口階段預先掃整個 `ai-system/skills/` 或 `ai-system/knowledge/` 目錄。

## 3. 高回頭成本停下 gate

一般任務只需要判斷一件事：如果方向錯了，回頭成本是否很高。

以下情況通常要先停下：

- 任務方向、需求理解、成功條件或影響範圍不明
- 存在多種合理方案，且會明顯影響產品行為、維護成本、資料狀態或協作流程
- 每一步都可局部執行，但整體產出若不符合預期，仍會難以回復、難以驗證或需要大量重做
- 關鍵依賴失效，繼續執行會用猜測或舊資料取代必要證據
- 會形成共享協作承諾，例如 commit、push、PR、merge、release、deploy 或對外發布

停下、請使用者判斷方向、選方案，或解釋尚未完全確定的結論時，先用 3-7 行摘要：

1. 結論或建議，以及目前理解的成功條件
2. 已確認事實與推測 / 假設
3. 主要風險或取捨
4. 驗證方式
5. 下一步

影響判斷的不確定性必須放在前面，不得只埋在細節裡。

低回頭成本、本機可逆、可快速驗證的工作可直接執行。

## 4. 補充原則

- 任務若已有明確路由，應優先沿既有路由執行，而不是每次重建流程。
- agent 應主動提出更好的做法、規則摩擦或路由缺口；被限制的是高回頭成本行動，不是思考與改良建議。
- 各任務工作流優先看命中的 workspace skill：`ai-system/skills/`。未命中 skill 或 skill 沒有指示時，再看 `ai-system/knowledge/`。
- 需要判斷制度 / 知識 / 安全網分工時，看 `ai-system/governance/contracts.md`；需要判斷制度設計、制度摩擦或治理演化時，看 `ai-system/governance/principles.md`。歷史紀錄、摩擦紀錄與提案只有制度審計與知識治理任務才主動讀。
