# 治理

本檔只處理三件事：

1. 制度為什麼存在
2. 制度應怎麼被設計
3. 經驗、知識與制度應如何演化

本檔不承載任務入口、日常操作方式、具體停下 gate 或文件導引。

制度 / 知識 / 安全網的完整責任契約見 `ai-system/governance/contracts.md`；本檔只展開制度目的、設計原則與治理原則。

## 1. 制度精神

制度存在的目的，不是單純限制 agent，而是降低整體協作成本。

這個成本包含：

- 回頭成本：方向做錯後重做、回復、重新對齊的成本
- 精神成本：使用者對越界、漏判、停錯與失誤的擔憂
- 時間成本：使用者處理低價值瑣事，以及 agent 重查、重問、重做的耗時
- 認知成本：規則難找、層級混亂、例外過多、判準不清
- 決策成本：使用者判斷方向、風險、取捨與下一步所需的精力與時間
- 協作成本：進入共享流程前後的確認與往返
- 維護成本：制度與知識持續膨脹造成的更新負擔

制度應優先降低使用者的決策成本：在高回頭成本任務中降低方向誤判，讓影響判斷的不確定性前置揭露，並讓使用者把注意力保留給高價值決策。

agent 回應應以降低決策成本為準：先給結論與關鍵風險，證據、推理與替代方案按需要後置；高回頭成本停下時的摘要格式見 `ai-system/rules.md`。

精簡不代表省略風險；揭露不確定也不代表凡事停下詢問。判準是是否降低使用者的決策成本。

## 2. 設計原則

### 成本導向

- 制度的評估標準，優先看是否降低整體成本，而不是條文是否完整
- 制度修改應優先處理高頻、高成本摩擦，而不是平均處理所有情況
- 若某條規則正確但長期增加大量澄清、等待或誤判成本，應重新設計

### 認知負擔最小化

- 制度應降低 agent 的認知負擔，而不是要求 agent 記住大量例外
- 能由骨架解決的問題，不應交給 agent 每次臨場判讀
- 若例外愈來愈多，應優先懷疑骨架錯了，而不是繼續補條款

### 讀者與任務情境分層

- 每段制度文字都應先判斷主要讀者：日常任務 agent、特定 skill agent、制度 / 知識維護 agent，或工具 / 安全邊界維護者
- 只在制度制定、路由整理、知識治理或工具維護時才需要知道的內容，不應放進日常任務入口
- `rules.md` 只放一般任務執行當下必須內化的最小判準；不得要求日常任務 agent 理解制度維護政策、目錄治理理由或遷移策略
- 若一段文字是在告訴制度維護者「制度應如何整理」，而不是告訴執行任務的 agent「此刻應如何行動」，應落在治理原則、制度審計 skill、知識治理 skill、細則或工具文件

### 單一事實來源與情境化提醒

- 需要維護一致性的規則、路由與判準，只保留一份正式來源
- 入口文件與流程文件可保留高風險或高回頭成本提醒，但提醒應短、應指回正式來源，不重列完整規則
- 重複提醒的目的只是不讓 agent 在高風險或高回頭成本節點漏判，不應讓後續維護者無法判斷哪份為準

### 安全責任分層

- 唯讀、非機密、本機可回退的操作應自動執行，不必每次停下詢問；過度停下本身是時間與決策成本
- 跨出本機、形成共享協作承諾、不可逆或高回頭成本，才需停下對齊
- 真正的安全由環境、權限等機械邊界承擔，不主要依賴 agent 自制；命令級權限與 approval 屬執行面，具體命令分類以 `ai-system/safety-net.md` 為唯一正式來源
- 制度主要處理任務語意層的決策 gate，尤其是高回頭成本，而不是代替環境承擔硬保護
- 日常入口規則不應要求一般任務 agent 內化命令級 permission table，或重複判斷工具層已能攔截的 approval
- 若某類違規反覆發生且可被機械攔截，應優先升級為工具或環境保護
- 安全網的責任邊界與變更規則以 `ai-system/governance/contracts.md` 與 `ai-system/safety-net.md` 為準

### 現況優先

- 真實行為證據與系統現況優先於文件與歷史說法
- 若制度文字與真實行為持續不一致，應以真實摩擦反推制度缺陷
- 若現況、口頭規範與正式文件不一致，應主動區分哪個是現況、哪個是規格、哪個是缺口

## 3. 治理原則

### 制度與知識分工

- 制度負責穩定的上位判準與決策 gate
- 知識負責描述現況、邊界、查詢方式與已驗證事實
- 流程文件負責可重複工作的操作路徑
- 制度只約定知識與安全網的目的、邊界、更新條件與信任方式，不內嵌其全文

不應把會快速變動的目前作法混進治理主文。

### 認知層與實踐層

- 知識治理應同時從兩個面向思考：**認知層**處理事實、現況、命名、查法與判準；**實踐層**處理做法、流程骨架與可重用執行能力。
- 認知層與實踐層是治理面向，不是互斥分類。

### 經驗內化判準

- 所有知識與做法在正式沉澱前，都應先標註**來源**與**查證程度**；未完成查證者，不得寫成已驗證事實。
- 已驗證且可重用的事實，應沉澱為知識
- 可反覆重用的任務流程，應沉澱為流程文件
- 實踐層內容的治理，應明確判定**機械化程度**，再決定應保留為經驗、沉澱為流程，或升級為 script、skill、template 或其他工具化形式。
- 反覆出現的制度摩擦，應先記錄並分析根因
- 高頻、高成本、可穩定抽象化的摩擦，才應升級為制度

不是所有經驗都值得升級為制度；只有明顯降低後續成本的內容，才應進入制度層。

### 骨架優先於例外

- 若同類例外持續增加，應優先懷疑骨架設計錯了
- 若某條規則需要大量補註才能成立，應考慮重寫或降級
- 若某類問題更適合由環境或工具攔截，不應繼續以文字制度承擔

### 治理修改的判準

修改制度時，應優先回答：

1. 這次修改要降低的是哪一種成本
2. 這個問題應由制度、知識、安全網還是流程承擔
3. 這是在修正骨架，還是在堆新的例外
4. 修改後是否會提高 agent 的認知負擔
5. 這項內容是否真的穩定到值得進入制度層
6. 這段文字的主要讀者是誰，是否真的需要日常任務 agent 在執行任務時看到
7. 是否需要同步更新 `ai-system/governance/contracts.md` 或 `ai-system/safety-net.md`

提出可直接執行的制度修改方案前，必須完成跨層一致性檢查；操作步驟見 `ai-system/skills/system-audit/SKILL.md` 的「跨層一致性檢查」。

- 凡屬制度骨架、分層、路由、分類法調整，若缺版本控制或其他低成本回退機制，視為高回頭成本修改，應先提案後落檔。
