# 治理

本檔只處理三件事：

1. 制度為什麼存在
2. 制度應怎麼設計
3. 經驗、知識與制度應如何演化

本檔不承載任務入口、日常操作方式、具體停下 gate 或文件導引。

portable core 的上位責任模型是「制度、知識、安全網」。完整契約見 `ai-system/contracts.md`；本檔只展開制度目的與治理原則。

## 0. 責任模型

- 制度是控制面：定義目標、判準、分工與變更規則。
- 知識是事實面：保存已驗證事實、查證路徑、制度脈絡、安全網脈絡與知識放置規則。
- 安全網是執行面：用 sandbox、hook、permission、approved scripts 或其他機械式保護降低越界風險。

制度不應把知識與安全網全文塞回主文；制度只約定它們的目的、邊界、更新條件與信任方式。

## 1. 制度目的

制度存在的目的，不是單純限制 agent，而是降低整體協作成本。

成本包含：

- 回頭成本：方向做錯後重做、回復、重新對齊的成本
- 精神成本：使用者對越界、漏判、停錯與失誤的擔憂
- 時間成本：使用者處理低價值瑣事，以及 agent 重查、重問、重做的耗時
- 認知成本：規則難找、層級混亂、例外過多、判準不清
- 決策成本：使用者判斷方向、風險、取捨與下一步所需的精力與時間
- 協作成本：進入共享流程前後的確認與往返
- 維護成本：制度與知識持續膨脹造成的更新負擔

制度應優先降低使用者的決策成本。在高回頭成本任務中，制度要降低方向誤判，讓影響判斷的不確定性前置揭露，並讓使用者把注意力保留給高價值決策。

制度也應降低使用者的精神負擔：讓使用者不必擔心 agent 亂衝、漏判、停錯或不做事。

agent 回應應預設精簡扼要，先給結論、關鍵風險與下一步；證據、推理與替代方案按需要後置補充。

真正的安全應優先由環境邊界、權限控制、sandbox、hook 或其他機械式保護承擔，而不是主要依賴 agent 自制。

若制度本身增加大量無謂審查、澄清或等待，應重新設計，而不是把成本轉嫁給使用者。

## 2. 設計原則

### 成本導向

- 制度的評估標準，優先看是否降低整體成本，而不是條文是否完整。
- 制度修改應優先處理高頻、高成本摩擦。
- 若某條規則正確但長期增加大量澄清、等待或誤判成本，應重新設計。

### 認知負擔最小化

- 制度應降低 agent 的認知負擔，而不是要求 agent 記住大量例外。
- 能由骨架解決的問題，不應交給 agent 每次臨場判讀。
- 若例外愈來愈多，應優先懷疑骨架錯了，而不是繼續補條款。

### 讀者與任務情境分層

- 每段制度文字都應先判斷主要讀者：日常任務 agent、特定 skill agent、制度 / 知識維護 agent，或工具 / 安全邊界維護者。
- 只在制度制定、路由整理、知識治理或工具維護時才需要知道的內容，不應放進日常任務入口。
- `rules.md` 只放一般任務執行當下必須內化的最小判準。
- 若一段文字是在告訴維護者「制度應如何整理」，而不是告訴執行任務的 agent「此刻應如何行動」，應放在治理原則、制度審計 skill、知識治理 skill、細則或工具文件。

### 單一事實來源與情境化提醒

- 需要維護一致性的規則、路由與判準，只保留一份正式來源。
- 入口文件與流程文件可保留高風險或高回頭成本提醒，但提醒應短，且應指回正式來源，不重列完整規則。
- 重複提醒的目的只是不讓 agent 在高風險節點漏判，不應形成第二套權威。

### 安全責任分層

- 真正的安全責任應優先落在環境與權限邊界。
- 命令級 approval 應由 execution layer、sandbox、hook、command policy、`approved-scripts` 或其他機械式保護承擔。
- 制度主要處理任務語意層的決策 gate，尤其是高回頭成本。
- 日常入口規則不應要求一般任務 agent 內化命令級 permission table。
- 若某類違規反覆發生且可被機械攔截，應優先升級為工具或環境保護。

### 現況優先

- 真實行為證據與系統現況優先於文件與歷史說法。
- 若制度文字與真實行為持續不一致，應以真實摩擦反推制度缺陷。
- 若現況、口頭規範與正式文件不一致，應主動區分哪個是現況、哪個是規格、哪個是缺口。

## 3. 演化原則

### 制度與知識分工

- 制度負責穩定的上位判準與決策 gate。
- 知識負責描述現況、邊界、查詢方式與已驗證事實。
- 流程文件負責可重複工作的操作路徑。

不應把會快速變動的目前作法混進治理主文。

### 認知層與實踐層

知識治理應同時看兩個面向：

- 認知層：事實、現況、命名、查法與判準
- 實踐層：做法、流程骨架、可重用執行能力

這兩者是治理面向，不是互斥分類。

### 經驗內化判準

- 所有知識與做法在正式沉澱前，都應先標註來源與查證程度。
- 已驗證且可重用的事實，應沉澱為知識。
- 可反覆重用的任務流程，應沉澱為 workflow 或 skill reference。
- 實踐層內容應先判斷機械化程度，再決定保留為經驗、沉澱為流程，或升級為 script、skill、template 或其他工具。
- 反覆出現的制度摩擦，應先記錄並分析根因。
- 只有高頻、高成本、可穩定抽象化的摩擦，才值得升級為制度。

不是所有經驗都值得升級為制度。只有明顯降低後續成本的內容，才應進入制度層。

### 骨架優先於例外

- 若同類例外持續增加，應優先懷疑骨架設計錯了。
- 若某條規則需要大量補註才能成立，應考慮重寫或降級。
- 若某類問題更適合由環境或工具攔截，不應繼續以文字制度承擔。

### 制度修改判準

修改制度時，先回答：

1. 這次修改要降低的是哪一種成本
2. 這個問題應由制度、知識、安全網還是流程承擔
3. 這是在修正骨架，還是在堆新的例外
4. 修改後是否會提高 agent 的認知負擔
5. 內容是否穩定到值得進入制度層
6. 主要讀者是誰
7. 是否需要同步更新 `ai-system/contracts.md` 或 `ai-system/safety-net/README.md`

提出可直接執行的制度修改方案前，必須檢查 principles、`rules.md`、constraints、對應 skill 與紀錄是否一致。若存在跨層衝突，先揭露衝突與建議處理範圍，不要只做單點修補。
